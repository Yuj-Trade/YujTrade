## Phase 1: Redis endpoint and scheme

- Status: DONE
- Commit: `bed47d0` fix: make the Redis scheme and username configurable
- Errors addressed: 2 WARNING, and the cache being off for the whole run.

`ResourceManager` built `rediss://default:<token>@<host>:<port>` from literals,
and the configured host no longer resolved, so every start abandoned the cache.
The scheme was not configurable, which matters because the current endpoint's
port terminates plain RESP: connecting to it with `rediss://` fails with
`[SSL: WRONG_VERSION_NUMBER]`.

`SecretsManager` gained `REDIS_URL` (full override), `REDIS_USERNAME` and
`REDIS_SSL`; `build_redis_url()` assembles the URL and `redact_redis_url()`
keeps the password out of the log line. TLS options are passed to the client
only for `rediss://`. `.env` now points at the live endpoint with
`REDIS_SSL=false`.

Verified against the live endpoint: connect, `SET`/`GET`/`EX`/`TTL` round-trip,
and no password in any log record.

## Phase 2: one macro fetch per cycle

- Status: DONE
- Commit: `a0a3a1d` fix: fetch macro data once per cycle instead of once per symbol
- Errors addressed: the 653 rate-limit waits and the 318-second unfinished run.

Three defects compounded:

- `AlphaVantageFetcher` had two near-identical implementations,
  `get_macro_economic_data` and `get_comprehensive_macro_data`, each issuing
  eight requests with its own cache key. `get_all_indices` called one and
  `get_macro_data` the other: sixteen requests per cycle against a five-per-
  minute budget. Three of the eight series (`INFLATION`, `CONSUMER_SENTIMENT`,
  `RETAIL_SALES`) were fetched and never read.
- `_gather_external_data` runs once per `(symbol, timeframe)` and memoised only
  completed results. The ten concurrent analyses all missed the memo and each
  started its own fetch, so a single provider budget produced dozens of
  simultaneous waiters.
- `RateLimiter` logged one line per waiter per window round.

Now there is one implementation and one cache key, the five consumed series are
declared in `MACRO_SERIES` (which fits the free-tier budget exactly),
`get_macro_economic_data` is single-flight, and the cycle memo stores
`asyncio.Task` objects so concurrent analyses share one fetch per scope.
`derivatives`, `order_book` and `news` are memoised too (news by base asset),
and `end_run_cycle` cancels whatever is still pending. A failed source is
reported once per cycle instead of once per symbol. The limiter logs at most one
wait line per window per bucket and keeps its counter for the snapshot.

`MarketIndicesFetcher` no longer takes an `AlphaVantageFetcher`: scoring reads
`BTC.D`, `USDT.D`, `DXY` and `VIX` from the indices, never macro keys.

Verified with ten concurrent callers against the real fetcher: 5 HTTP requests
and 0 rate-limit sleeps. The old code issued 80 requests for the same work.

## Phase 3: transport failures are upstream outages

- Status: DONE
- Commit: `de3648e` fix: classify transport failures as upstream outages
- Errors addressed: all 14 ERROR lines.

`BaseFetcher._fetch_json` converted only `TimeoutError` and
`ClientConnectorError` into `UpstreamUnavailableError`.
`aiohttp.ServerDisconnectedError`, `ClientOSError`, `ClientPayloadError` and
`ServerTimeoutError` escaped raw, so the reporting helpers saw something that
was not an upstream outage and logged it at ERROR. `get_global_market_data` did
not use a helper at all.

`_fetch_json` now converts `TimeoutError`, `ConnectionError` and every
`aiohttp.ClientError`; `aiohttp.ClientResponseError` is re-raised first so an
HTTP error status keeps its previous contract and the breaker is not fed by
4xx/5xx bodies. `report_fetch_failure` moved to `data/sources/base_fetcher.py`,
replacing the two duplicate copies in `binance_fetcher` and `data_provider`, and
`MarketIndicesFetcher` now uses it.

## Phase 4: bounded Redis pool and degrading cache

- Status: DONE
- Commit: `4efcff0` fix: bound the Redis pool and let cache failures degrade
- Errors addressed: 10 ERROR found by the first live cycle after phase 1
  (`max number of clients reached`).

Enabling the cache exposed a limit that had been unreachable. With
`max_connections=50` the pool opened more clients than the server allows, and
redis-py raises `Too many connections` from the pool rather than waiting, so
every fetch whose cache lookup lost that race failed.

`utils/resilient_redis.py` wraps the client: `get`/`set`/`ping`/`aclose` absorb
`redis.RedisError`, return a miss or a no-op, and report once per five minutes
with a suppressed count. The client now uses `BlockingConnectionPool`, bounded
by `REDIS_MAX_CONNECTIONS` (default 10) and `REDIS_POOL_TIMEOUT` (default 10 s),
so a saturated pool queues instead of failing. The endpoint is ~200 ms away, so
queueing is the only correct behaviour.
